# Antigravity 2.0 발표 요약

## 1. 발표 개요

이 발표는 Google의 에이전트 기반 코딩 개발 플랫폼 **Antigravity 2.0**을 소개하고, 실제 개발에서 **Agent/Skill을 활용하는 방법**과 **Ralph 방식의 장시간 자율 개발 루프를 구성하는 방법**을 설명한다.

발표 전체를 관통하는 핵심 메시지는 다음과 같다.

> AI 코딩 에이전트를 잘 활용하려면 단순히 좋은 모델을 사용하는 것보다 **컨텍스트를 체계적으로 관리하고, 작업을 작게 나누며, 검증 가능한 완료 조건을 만드는 것**이 중요하다.

---

## 2. Antigravity란?

Antigravity는 단순히 프롬프트를 입력해 코드를 생성하는 도구가 아니라, 여러 개발 환경에서 동일한 에이전트 경험을 제공하는 **에이전트 기반 코딩 개발 플랫폼**으로 소개된다.

로컬, CLI, IDE 등 서로 다른 환경에서도 사용자 설정과 컨텍스트를 유지하는 **일관성**이 주요 특징이다.

### 핵심 철학

Antigravity의 기본적인 작업 방식은 다음 세 단계로 정리할 수 있다.

1. **Plan** — 무엇을 구현할지 계획한다.
2. **Act** — 실제 코드와 시스템을 변경한다.
3. **Verify** — 결과를 테스트하고 검증한다.

에이전트가 무작정 코드를 생성하는 것이 아니라 구현 계획, 변경 사항, 작업 결과 등을 남겨 사용자가 각 단계를 확인하고 제어할 수 있도록 하는 것이 핵심이다.

---

## 3. Antigravity 2.0의 변화

### 단일 에이전트에서 멀티 에이전트 구조로

Antigravity 1.0은 하나의 에이전트가 개발과 테스트 등의 작업을 처리하는 구조에 가까웠다.

2.0에서는 메인 에이전트가 작업을 판단한 뒤 필요에 따라 여러 **서브 에이전트**에게 작업을 나누어 수행할 수 있게 되었다.

이를 통해 메인 컨텍스트를 불필요하게 오염시키지 않으면서 작업을 분리할 수 있다.

또한 하나의 워크스페이스에만 한정되지 않고 프론트엔드, 백엔드, 인프라 등 여러 디렉터리를 포함하는 프로젝트를 함께 다룰 수 있는 방향으로 확장되었다.

그 밖에도 스케줄 작업, 에이전트 간 통신 등 여러 기능이 추가되면서 단순한 코딩 도구보다는 **확장 가능한 코딩 플랫폼**에 가까워지고 있다는 것이 발표자의 평가다.

---

## 4. Claude Code / Codex와의 비교

발표자의 관점에서 각 도구의 강점은 다음과 같이 정리된다.

### Antigravity

- 가성비가 주요 장점
- Google/Gemini 생태계와의 결합
- 학생에게 제공되는 무료 사용 혜택
- 아직 Agent/Skill 커스터마이징 생태계는 상대적으로 부족

### Claude Code

- Agent, Skill 등 **커스터마이징 생태계가 성숙**
- 관련 도구와 자료가 풍부

### Codex

- Slack 등 **서드파티 서비스와의 연결 및 협업 기능**이 강점
- CLI/API 등을 활용한 다양한 사용 방식에서 유연성이 있음

즉 발표자는 하나의 도구가 모든 면에서 우월하다기보다 각각 장점이 다르다고 평가한다.

---

## 5. 프롬프트를 반복하지 말고 Agent / Skill을 활용하라

발표에서 실전 활용 방법으로 강조하는 부분 중 하나다.

반복해서 수행하는 작업이라면 매번 긴 프롬프트를 작성하기보다는 작업 방법을 **Agent 또는 Skill로 정의하여 재사용**하는 것이 효율적이다.

예를 들어 발표자는 PM/PO 업무를 하면서 기술적인 작업 내용을 문서화할 일이 많았는데, 기존 Technical Writer 계열 스킬의 한국어 결과가 만족스럽지 않아 직접 기술 문서 작성용 커스텀 에이전트를 만들었다고 설명한다.

커스텀 Agent/Skill을 만드는 방법 자체도 복잡하게 생각할 필요가 없다.

1. 원하는 작업 방식과 규칙을 Markdown 문서로 작성한다.
2. 해당 내용을 코딩 에이전트에게 제공한다.
3. 이 내용을 기반으로 Agent/Skill을 만들어 달라고 요청한다.
4. 생성된 Agent/Skill을 이후 작업에서 재사용한다.

즉 **AI를 이용하여 AI가 사용할 작업 지침 자체를 만드는 방식**이다.

---

# 6. Ralph 방식의 자율 개발

발표 후반부의 핵심 주제다.

Ralph는 코딩 에이전트에게 작업을 맡긴 뒤 사람이 계속 개입하지 않아도 다음과 같은 루프를 반복하도록 만드는 자동화 패턴이다.

```text
요구사항 확인
    ↓
구현
    ↓
테스트
    ↓
실패 원인 분석
    ↓
수정
    ↓
재테스트
    ↓
완료 조건 만족 시 종료
```

목표는 사람이 밤에 작업을 실행해 놓더라도 에이전트가 스스로 구현과 테스트를 반복하여 가능한 범위에서 작업을 완료하도록 만드는 것이다.

다만 발표자는 Antigravity의 구조적 특성 때문에 일반적인 Ralph 루프를 그대로 적용하기보다 별도의 컨텍스트 관리 구조를 사용했다고 설명한다.

---

## 7. 한 번에 Task 하나만 수행한다

발표자가 실제로 여러 방식으로 테스트하면서 발견한 중요한 원칙이다.

여러 개의 작업을 동시에 수행시키면 컨텍스트가 섞이면서 작업 품질이 떨어지는 문제가 발생했다.

따라서 다음과 같은 방식을 권장한다.

```text
Task 1 선택
    ↓
구현
    ↓
테스트
    ↓
결과 기록
    ↓
Task 2 선택
    ↓
...
```

즉 **한 번에 하나의 Task만 수행하고 순차적으로 처리한다.**

병렬로 많은 작업을 던지는 것보다 작업 범위를 작게 제한하여 에이전트가 현재 목표에 집중하도록 만드는 것이 중요하다.

---

# 8. Context를 AI의 기억에만 맡기지 않는다

발표에서 가장 중요하게 강조되는 실전 원칙 중 하나다.

LLM에게 단순히 "이 내용을 기억해"라고 하는 것만으로 장시간 개발 작업의 상태를 관리해서는 안 된다.

컨텍스트가 길어질수록 이전 내용을 놓치거나 중요한 요구사항을 잊을 가능성이 있기 때문이다.

따라서 중요한 상태는 **외부 파일에 기록**한다.

대표적으로 다음과 같은 구조를 사용한다.

### PRD

에이전트가 수행해야 할 요구사항과 완료 조건을 정의한다.

### Progress.txt

현재까지 어떤 작업을 했는지 기록한다.

특히 기존 내용을 수정하거나 삭제하기보다 **append-only 방식으로 계속 추가**하는 것을 권장한다.

이전 실패와 시도까지 남겨두어야 이후 에이전트가 무엇이 잘못되었는지 파악하고 개선할 수 있기 때문이다.

### Git Log

실제 코드가 어떻게 변경되었는지 추적한다.

결과적으로 다음과 같은 역할 분담이 만들어진다.

```text
LLM Context
→ 현재 작업을 위한 단기 기억

PRD / Progress / Git
→ 작업 전체를 유지하는 장기 기억
```

# 9. PRD의 품질이 결과물의 품질을 결정한다

자율 개발에서는 사람이 중간에 계속 개입하지 않기 때문에 처음 제공하는 요구사항이 매우 중요하다.

단순히 기능을 설명하는 것만으로는 부족하고 **검증 가능한 완료 조건**을 작성해야 한다.

예를 들어 다음과 같은 요구사항보다

```text
로그인 기능을 만들어라.
```

다음과 같은 요구사항이 더 좋다.

```text
로그인 POST API를 구현한다.
정상적인 사용자 정보로 요청했을 때 HTTP 200을 반환해야 한다.
해당 조건을 확인하는 테스트가 통과해야 한다.
```

즉 PRD에는 단순히

> 무엇을 만들어야 하는가?

뿐만 아니라

> 어떤 상태가 되면 이 Task가 완료된 것인가?

까지 정의되어야 한다.

---

# 10. 최대 Iteration을 제한한다

자율 개발 루프를 제한 없이 실행하면 다음과 같은 상황이 발생할 수 있다.

```text
테스트 실패
→ 수정
→ 테스트 실패
→ 수정
→ 테스트 실패
→ ...
```

에이전트가 끝없이 문제를 해결하려고 하면서 토큰과 사용량을 소비할 수 있다.

따라서 **Maximum Iteration**을 설정해 일정 횟수 이상 실패하면 작업을 중단하도록 만드는 것을 권장한다.

예를 들면 다음과 같다.

```text
Task 실행
   ↓
구현
   ↓
테스트
   ↓
성공 ─────────→ 완료
   │
   └ 실패
       ↓
      수정
       ↓
   최대 N회 반복
       ↓
   초과 시 중단 및 기록
```

# 11. 발표에서 제안하는 자율 코딩 하네스 구조

발표 후반부의 내용을 구조화하면 다음과 같이 정리할 수 있다.

```text
PRD
│
│ 요구사항 + 완료 조건
↓
Task Queue
│
│ 한 번에 Task 하나 선택
↓
Coding Agent
│
│ 구현
↓
Test / Verification
│
├─ 성공 → Progress 기록 → Git 기록 → 다음 Task
│
└─ 실패 → 원인 분석 → 수정 → 재테스트
                       │
                       └─ Maximum Iteration 제한
```

그리고 작업 상태는 별도의 파일에 유지한다.

```text
PRD.md
    └─ 무엇을 해야 하는가?

Progress.txt
    └─ 지금까지 무엇을 했는가?

Git Log
    └─ 실제 코드가 어떻게 변경되었는가?
```

새로운 세션이 시작되더라도 이 파일들을 다시 읽으면 이전 작업 상태를 복구할 수 있도록 만드는 것이다.

---

# 12. 핵심 원칙 정리

발표 내용을 실전 원칙으로 압축하면 다음과 같다.

1. **큰 작업을 작은 Task로 분리한다.**
2. **한 번에 하나의 Task에 집중시킨다.**
3. **PRD에 검증 가능한 완료 조건을 작성한다.**
4. **작업 진행 상황을 LLM Context에만 의존하지 않는다.**
5. **Progress 파일과 Git을 이용해 외부에 상태를 저장한다.**
6. **실패 기록도 삭제하지 않고 다음 작업의 컨텍스트로 활용한다.**
7. **테스트를 통해 완료 여부를 판단한다.**
8. **Maximum Iteration으로 무한 반복을 방지한다.**
9. **반복되는 작업 방식은 Agent/Skill로 만들어 재사용한다.**
10. **좋은 모델보다 좋은 Context 관리 구조가 중요하다.**

---

# 결론

이 발표에서 Antigravity 2.0 자체의 기능 소개도 중요한 부분이지만, 더 일반적으로 활용할 수 있는 핵심은 후반부의 **AI 코딩 에이전트 운영 방법론**이다.

핵심 구조는 다음과 같이 압축할 수 있다.

```text
PRD
  ↓
작은 Task
  ↓
Agent 구현
  ↓
Test
  ↓
Progress 기록
  ↓
Git 기록
  ↓
Fresh Context
  ↓
다음 Task
```

결국 장시간 자율 코딩의 품질을 결정하는 것은 단순한 모델 성능이 아니라 **명확한 요구사항, 작은 작업 단위, 검증 가능한 테스트, 외부 상태 저장, 그리고 체계적인 컨텍스트 관리**라고 정리할 수 있다.
